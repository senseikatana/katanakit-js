# Plan: corregir la regresión de versiones en el bot de releases

## Problema confirmado

`determine-version.sh` usa `git describe --tags --abbrev=0`, que devuelve el tag **más cercano en el historial**, no el de **mayor versión semántica**. Cuando las ramas divergen (p. ej. `dev` vs `main`), el bot puede calcular una versión **menor** a una ya publicada. Evidencia real: existe `v2.2.3` creado **después** de `v2.3.0`.

## Cambio

### `determine-version.sh` (línea 12)

Reemplazar:
```bash
latest_tag="$(git describe --tags --abbrev=0 2>/dev/null || echo "")"
```
por una búsqueda por **máxima versión semántica**:
```bash
latest_tag="$(git tag --sort=-v:refname 2>/dev/null | head -n 1)"
```

`--sort=-v:refname` ordena por versión (maneja correctamente `v2.10.0 > v2.9.0`), garantizando que el bump siempre parta de la versión más alta publicada, sea cual sea la rama. Si no hay tags, `latest_tag` queda vacío y el comportamiento actual (empezar en `v0.1.0`) se mantiene.

### `release.sh` (red de seguridad adicional)

Tras calcular/normalizar `tag_name`, añadir una verificación **monótona**: si el `tag_name` ya existe como tag local o remoto, o si es **menor o igual** a la máxima versión existente, detenerse sin publicar (aviso claro). Esto blinda el caso de que alguien escriba una versión menor manualmente en "Run workflow".

## Verificación

- `bash -n` en ambos scripts.
- Prueba en repo temporal simulando divergencia de ramas: publicar `v2.3.0` en una rama, luego correr el cálculo en otra con commits nuevos → debe producir `v2.3.1` (o `v2.4.0` si hay `feat`), **nunca** `v2.2.x`.
- Prueba de monotonicidad: pasar `v2.2.3` cuando ya existe `v2.3.0` → debe rechazarse.
