Access Control ​

access.service.ts answers one question: may this subject do this thing? It ships no identity provider. Authentication is somebody else's job.

Authentication vs Authorization ​

These are two different questions, and conflating them is one of the most common causes of a security bug.

AuthenticationAuthorization
QuestionWho are you?What may you do?
VerifiesA credentialA permission
InputPassword, token, session cookie, OAuth callbackA subject and a capability
Failure means401 Unauthorized403 Forbidden
Implemented byBetter Auth, your IdP, your session layerAccessService
PageBetter AuthThis page

They are independent. You can be perfectly authenticated and still not allowed to do something — that is the normal case for an ordinary user hitting an admin route. And a request can be neither authenticated nor authorized: it never got far enough to be identified.

The order matters, and this is where hand-rolled guards usually go wrong:

ts
// 1. Who is this?          -> null means we do not know. 401.
// 2. May they do this?      -> false means we know, and no. 403.
const subject = resolveSubject(request);

if (!subject) return response.status(401).end();       // Authentication failed
if (!useCan(subject, "content:publish")) {
  return response.status(403).end();                    // Authorization failed
}

Returning 403 for an unknown subject is the classic error: it tells an anonymous attacker that the route exists and that some account would be allowed, which is reconnaissance for free. Returning 200 because the subject is unknown is worse. useRequireCapability() implements both steps in the right order, and fails closed on a malformed subject.

Where the boundary sits ​

ts
import { useRequireCapability } from "katanakit-js/adapters/express";

The guard never authenticates. You hand it a function that maps the request to a subject — a JWT payload, a session row, an API key lookup:

ts
useStartAssistant(3000, "localhost", "/assistant", {
  guard: useRequireCapability("conversations:use", (request) => request.account ?? null),
});

Returning null produces 401. A subject without the capability produces 403.

The roles ​

Six built-in roles, ordered from most to least privileged. Every role inherits everything from the roles below it, so the table lists only what each role adds.

RoleRankAddsEffectively can
owner0roles:assign, system:adminEverything, including granting roles and administering the system. The developer seat.
admin1members:manageEverything an owner can, minus role assignment — manage members
editor2content:publish, content:edit:any, content:delete:any, conversations:moderateEdit and delete anyone's content, publish, moderate conversations
author3content:create, content:edit:own, content:delete:ownCreate content and manage only their own
member4conversations:useUse the assistant, nothing else
guest5(none)Read-only, where reading is public

The hierarchy is the point: an editor can publish because publishing is above them in the rank, not because it was listed for them.

ts
useCan({ id: 1, roles: ["editor"] }, "content:publish");     // true  (inherited + own)
useCan({ id: 1, roles: ["editor"] }, "content:edit:any");    // true  (own)
useCan({ id: 1, roles: ["editor"] }, "roles:assign");        // false (above)
useCan({ id: 2, roles: ["author"] }, "content:edit:any");    // false (below)

owner is the developer seat ​

owner sits above admin on purpose and exists for a specific person: you, the developer, or whoever runs the deployment. It is the only role that can grant other roles (roles:assign) and the only one with system:admin.

In practice this is how you keep yourself out of day-to-day user management. Give staff admin — they manage members, content and conversations. Keep owner for the handful of accounts that configure the system itself.

Do not hand owner to a shared account. It is a single point of compromise that bypasses every other role. One named human (plus a break-glass account in a password manager) is the usual shape.

Capabilities ​

Capabilities are namespaced strings, <domain>:<action>[:<scope>]. The scope suffix is what keeps edit:own and edit:any from being confused:

CapabilityMeaning
content:createCreate a draft
content:publishPublish — the editor's threshold
content:edit:own / content:delete:ownAct on your own content only
content:edit:any / content:delete:anyAct on anyone's content
conversations:useTalk to the assistant
conversations:moderateModerate other users' conversations
members:manageInvite, remove and change user roles
roles:assignChange which role a user holds
system:adminSystem-level administration

A subject is structural, not a database row:

ts
interface AccessSubject {
  id: string | number;
  roles: AccessRole[];
}

That keeps the core free of any persistence concern — a Prisma Account, a JWT payload and a test fixture all satisfy it.

ts
useCan({ id: user.id, roles: user.roles }, "content:publish");

The two strategies ​

AccessService resolves capabilities through a strategy, and ships two.

HierarchicalAccessStrategy (default) — a role inherits every capability of the roles below it, per the table above.

FlatAccessStrategy — no inheritance. A role grants exactly the capabilities listed for it, nothing more. Use it when a role must be exactly what it says — for example, granting author without the conversations:use that author would otherwise pick up from member.

ts
import { AccessService, FlatAccessStrategy } from "katanakit-js";

AccessService.getInstance().useSetStrategy(new FlatAccessStrategy());

Under the flat strategy the built-in table must list each role's complete capability set, because nothing is inherited. Check useRoles() for the resolved registry before relying on it.

Subjects can hold several roles ​

Roles union — a subject is allowed anything any of their roles allows. This is how you model "an author who is also a support agent" without inventing a new role.

ts
const subject = { id: 7, roles: ["member", "author"] };

useCan(subject, "conversations:use");  // true  — from member
useCan(subject, "content:create");     // true  — from author
useCan(subject, "conversations:moderate"); // false

Extending the registry ​

useRegisterRole adds or replaces a definition. Because capabilities are a Zod enum, a custom role must reuse existing capabilities — the registry is designed for a fixed vocabulary of permissions with a new grouping of them, not for inventing permissions per tenant.

ts
import { useRegisterRole } from "katanakit-js";

useRegisterRole({
  slug: "moderator",           // needs a custom AccessRole schema first
  label: "Moderator",
  capabilities: ["conversations:use", "conversations:moderate"],
});

slug and the capabilities are format-validated strings, not a closed enum, so a role the domain needs is registerable directly. What you lose is the compile-time check on a misspelled built-in slug: it now fails at runtime with Unknown access role instead of at build time. Prefer assigning existing roles unless the domain genuinely needs a new one.

Registering your own roles ​

rank lives on the definition, so a registered role inherits from the built-ins on equal terms. A deployment that reports on fiscal quarters registers the unit it actually uses:

ts
import { useRegisterRole, useResetRoles } from "katanakit-js";

useRegisterRole({
  slug: "rrhh",
  label: "RRHH",
  // Lower rank = more privileged. Anywhere from `member` (4) upward inherits
  // the assistant capability; above `editor` (2) it also inherits publishing.
  rank: 3,
  capabilities: ["nomina:aprobar", "expediente:firmar"],
});

useCan({ id: 1, roles: ["rrhh"] }, "nomina:aprobar");  // true
useCan({ id: 1, roles: ["rrhh"] }, "content:create");   // inherited from author
useCan({ id: 1, roles: ["rrhh"] }, "content:publish");  // false — below editor

useRegisterRole() validates before storing and throws with the offending field on a bad definition. A malformed role cannot silently poison the registry — the failure is loud and immediate.

useResetRoles() restores the built-ins — useful between tests, since the registry is process-global.

Ownership is not a capability ​

A role answers what kind of thing a subject may do; it does not answer which instance. content:edit:own says "edit your own content", and enforcing the "own" part is still your job:

ts
router.put("/articles/:id", (req, res) => {
  const subject = resolveSubject(req);
  if (!subject) return res.status(401).end();
  if (!useCan(subject, "content:edit:any")) {
    const article = load(req.params.id);
    // The "own" half needs the resource, not the role.
    if (article.authorId !== subject.id) return res.status(403).end();
  }
  res.json(update(req.params.id, req.body));
});

Skipping the resource check and trusting edit:own alone is an IDOR. The role narrows the set; your handler confirms membership.

Resource grants — a role scoped to one thing ​

A global role answers "what class of thing may this person ever do". It does not answer "may they do it to this document". The moment someone is given access to one file and nothing else, you need a second axis.

A Grant is a role scoped to a resource, using the same registry — so viewer, commenter and editor mean whatever your deployment registered them to mean. There is one vocabulary, not two.

ts
import { useGrantAwareCan } from "katanakit-js";

const decision = useGrantAwareCan({
  subject,                                    // from useResolveSubject()
  resource: { type: "expediente", id: 42 },
  capability: "expediente:read",
  useGrants: ({ subject, resource }) => listShares(subject.id, resource),
});

decision.allowed; // boolean
decision.source;  // "role" | "grant" | "none" — why, for your audit log
decision.via;     // the granted role, when source is "grant"

Global roles are checked first, then grants for that exact resource. Three invariants worth knowing:

  • Expiry is evaluated by the core, not by your resolver, so revoking access is deleting one row rather than auditing every query that might have cached the role. A Grant may carry expiresAt.
  • An unreadable expiresAt counts as expired, not as open. A share whose deadline cannot be parsed is a share nobody meant to leave running.
  • A missing useGrants denies. It does not skip the check — a typo in the resolver name must not open a route.

The authentication seam ​

AccessService answers what may you do. It does not answer who are you, and it must never learn which provider produced that answer. The kit normalises the credential result into a single Principal so this page's logic never branches on it.

ts
import { AuthService, useResolveSubject } from "katanakit-js";
import { useBetterAuthProvider } from "katanakit-js/adapters/better-auth";

AuthService.getInstance().useRegister(useBetterAuthProvider(auth));

// The seam between the two concepts. The role lookup is injected, so the core
// stays free of I/O.
const subject = await useResolveSubject("better-auth", request, (principal) =>
  directory.rolesFor(principal.subject),
);

Three results, and the difference between the first two is the whole point:

SituationResult
Nobody signed in{ ok: true, data: null } → answer 401
Signed in, no roles{ ok: true, data: { roles: [] } } → answer 403
The provider failed{ ok: false, error } → answer 500

An anonymous visitor is a value, not an error. Collapsing it into a failure turns a broken identity provider into a public route, and the symptom reads as "nobody is logged in" rather than "the backend is down". An unknown provider id is ok: false for the same reason — a typo must not quietly open a guard.

A credential method never grants elevation. Signing in with Google proves "I control this account" — a genuinely strong claim — and says nothing about employment. A deployment that allows self-registration therefore creates an identity with no scope and no elevated role; elevation requires someone with the authority to grant it.

The same reasoning keeps your own role table even with SSO: a personal email account has no concept of your employment relationship and cannot be revoked on offboarding. Only your table can say no.

The user directory ​

DirectoryService wraps a repository you implement and enforces the rules that otherwise live in a code review nobody reads:

ts
import { DirectoryService } from "katanakit-js";

const directory = new DirectoryService({ repository });

await directory.useList({ limit: 50, role: "admin" });
await directory.useAddRole(actor, id, "editor");
await directory.useRemoveRole(actor, id, "editor");
await directory.useSuspend(actor, id, "contract ended");
await directory.useReactivate(actor, id);
await directory.useDelete(actor, id);

The invariants:

  • The last active holder of a role cannot lose it. A suspended holder does not rescue them — counting them would let the system drop to zero live administrators. The refusal names the way out: promote someone else first.
  • Nobody may suspend, delete or demote themselves. Removing your own roles is the change with no undo and no second pair of hands.
  • You cannot grant a role more privileged than the best one you hold. A role you could never grant is a role you may never revoke either — that is the direction privilege is lost, and the direction an attacker moves in.
  • owner is never assigned through these paths. Use a dedicated ownership transfer; useUpdate({ roles: ["owner"] }) is refused too, not just useAddRole.
  • useSuspend is soft offboarding, and it is not useDelete. Removing the row loses the evidence the account existed; leaving it "inactive" in a provider with no such state means the person can still sign in.

Every refusal carries a stable code — last_owner, self_suspension, privilege_escalation, already_suspended, deactivated_identity — so a UI can branch on it instead of matching message text:

ts
const result = await directory.useSuspend(actor, id);
if (!result.ok && result.error.code === "last_owner") {
  showMessage("Promote another owner before suspending this account.");
}

Deliberately not here: deleting a provider account, revoking a live session or forcing a password change. A directory row disappearing must never be the only thing that happens on offboarding — those belong to the provider you actually use.
